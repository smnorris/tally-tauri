# Tally data file format

This documents the shape of every file Tally persists to disk, as a reference
for future changes. It reflects the actual code in `src/App.jsx` — if you
change a record shape, update this file in the same commit.

## Storage location

```
~/Library/Application Support/<identifier>/
```

`<identifier>` is whatever's set in `src-tauri/tauri.conf.json` (`identifier`
field) — currently `com.example.tally`, but you're expected to change this
before distributing (see README).

Each table is one plain JSON file: `<table-name>.json`, containing a JSON
array of records (or `null`/missing if never written). Reads/writes go
through `src/storage.js`, which calls into `src-tauri/src/lib.rs`'s
`read_json`/`write_json` commands — plain `std::fs` read/write, no encoding
tricks, no locking.

## Tables

| Table constant | Filename | Contents |
|---|---|---|
| `TABLES.clients` | `clients.json` | `Client[]` |
| `TABLES.projects` | `projects.json` | `Project[]` |
| `TABLES.tasks` | `tasks.json` | `Task[]` |
| `TABLES.entries` | `time-entries.json` | `TimeEntry[]` |
| `TABLES.shownRows` | `timesheet-shown-rows.json` | `ShownRow[]` |

All IDs (`id`, `clientId`, `projectId`, `taskId`) are strings generated by
`crypto.randomUUID()` (see `uid()` in `App.jsx`).

---

### Client

```ts
{
  id: string;
  name: string;
  archived?: boolean;   // omitted/false = active
}
```

- No `clientId`-style foreign key — clients are the root of the hierarchy.

---

### Project

```ts
{
  id: string;
  name: string;
  clientId: string;        // -> Client.id
  budgetAmount: number;    // dollars; 0 = no budget set
  hourlyRate: number;      // dollars/hour; 0 = no rate set
  color: string;           // 6-digit hex, e.g. "#8dd3c7"
  archived?: boolean;
}
```

- `color` is expected to be one of the 10 fixed swatches in `PROJECT_COLORS`
  (see `App.jsx`), but nothing enforces that at the data layer —
  `projectTint()` falls back to `DEFAULT_PROJECT_COLOR` for anything that
  doesn't match `/^#[0-9a-fA-F]{6}$/`, so a malformed value degrades
  gracefully rather than crashing.
- `budgetAmount` and `hourlyRate` are always written as numbers (never
  omitted) by `addProject`/`updateProject`, defaulting to `0` via `|| 0`.

---

### Task

```ts
{
  id: string;
  name: string;
  projectIds: string[];   // -> Project.id, many-to-many
  archived?: boolean;
}
```

- **Legacy shape** (pre many-to-many): `{ id, name, projectId: string }`.
  Migrated automatically on load — see "Migrations" below. Once migrated and
  re-saved, the legacy `projectId` field is gone.
- A task with `projectIds: []` is valid (a task not currently assigned to
  any project) — the UI shows it as "No projects assigned" and it never
  appears on the timesheet.

---

### TimeEntry

```ts
{
  id: string;
  taskId: string;      // -> Task.id
  projectId: string;   // -> Project.id (which of the task's projects this entry belongs to)
  date: string;         // "YYYY-MM-DD", local calendar date, no timezone info
  hours: number;         // > 0; entries are deleted rather than stored as 0
  invoiced?: boolean;   // omitted/false = not invoiced
}
```

- **`(taskId, projectId, date)` is the effective unique key** — `setHours()`
  looks up by all three, and there's at most one entry per combination.
  This matters because a task can belong to multiple projects; hours must be
  attributed to one specific project, not just the task.
- **Legacy shape** (pre many-to-many): entries had no `projectId` at all — it
  was implied by the task's single project. Migrated automatically on load,
  using the task's original `projectId` at migration time. An entry that
  can't be resolved to a project this way (orphaned task reference) is
  dropped rather than kept in a broken state.
- **`invoiced` entries are locked**: `setHours()` refuses to modify an entry
  where `invoiced === true` (returns early, no-op). The UI also disables the
  input, but this is enforced at the data-mutation layer too, not just in
  the UI.
- Deleting a task, project, or client is **blocked** (not cascaded) if any
  of its entries have `invoiced: true` — see `deleteTask`/`deleteProject`/
  `deleteClient` in `App.jsx`. This is the one place "delete" doesn't
  cascade-destroy related data; everywhere else, deletion cascades freely.

---

### ShownRow

```ts
{
  id: string;
  weekKey: string;     // "YYYY-MM-DD" — the Monday of the week this applies to
  taskId: string;       // -> Task.id
  projectId: string;    // -> Project.id
}
```

- Represents "this task/project pairing is explicitly shown on the
  timesheet for this specific week." No entry = hidden by default.
- **A task/project pairing is also visible for a week if it has any logged
  `TimeEntry` for a date within that week**, regardless of whether a
  `ShownRow` exists — see `hasEntryThisWeek()` in `TimesheetTab`. This is
  computed at render time, not persisted; don't expect to find a `ShownRow`
  for every visible row.
- `weekKey` is always a Monday, computed via `getMonday()` — never validate
  or generate one that isn't.

---

## Migrations

Migrations run once, automatically, on app load (inside the `useEffect` in
`TallyApp`) and are one-directional — there's no "downgrade" path.

| From | To | Trigger | Where |
|---|---|---|---|
| `Task.projectId: string` | `Task.projectIds: string[]` | `!Array.isArray(task.projectIds)` | `App.jsx`, load effect |
| `TimeEntry` with no `projectId` | `TimeEntry.projectId` backfilled from the task's original `projectId` | `!entry.projectId` | `App.jsx`, load effect, uses a `legacyTaskProject` map built from the task migration above |

If you need to add a new migration, follow the existing pattern: detect the
old shape defensively (don't assume presence of new fields), transform, set
a `*Changed` flag, and only write back to disk if something actually
changed (`if (tasksChanged) safeWrite(...)`) — avoids rewriting files that
didn't need it on every single load.


---

## Adding a new field or table checklist

1. Update the shape here first — treat this file as the design doc, not an
   afterthought.
2. Decide the default for existing records that predate the field (usually:
   treat `undefined` as falsy/default in the reading code, rather than
   writing a migration, unless the field is load-bearing for correctness —
   see `invoiced`/`archived`/`color` for the "cheap default" pattern vs.
   `projectIds`/entry `projectId` for the "needs an explicit migration"
   pattern).
3. If it's a new table, add it to `TABLES` in `App.jsx` with a plain
   lowercase-hyphenated filename (no `tally:` prefix — that convention was
   specific to the in-chat artifact's key-value storage and doesn't apply
   here), and add a matching `readTable`/mock entry if tests need it.
4. Update `src/test/mockStorage.js` only if you add a new storage.js export
   (it mirrors that file's public API, not the app's data shapes directly).
